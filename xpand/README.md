# Xpand — Backend

Backend for **Xpand**, a Telegram Mini App used internally to track the company's daily
cash position by logging every income and expense. It pairs a fast UI with chat commands so
employees can record transactions in seconds, many times a day.

The **User**, **Category**, **Transaction**, **Reports** (cash position & balances), and
**Supplier / Product / Packaging** (with their many-to-many relationships) APIs are implemented
on top of an introspected Prisma schema, alongside **real Telegram authentication**, the
**Telegram bot**, and **invoice upload with OCR** — photograph an invoice and its supplier, date,
total, currency and invoice number are read for the user to verify before a transaction is created.

> **Auth is real.** Mini App `initData` signatures are validated against the bot token (see
> [Authentication](#authentication)). The old `x-telegram-id` header still works in development
> so the app is usable in a browser tab, and is **hard-refused when `NODE_ENV=production`**.

## Overview

- **Runtime:** Node.js (current LTS, ≥ 20)
- **Language:** TypeScript (strict), ESM modules
- **Framework:** Express
- **ORM:** Prisma (PostgreSQL)
- **Validation:** Zod
- **Logging:** pino + pino-http
- **Security:** helmet, cors, express-rate-limit
- **Tooling:** tsx, ESLint, Prettier

Capabilities: income/expense logging across 11 fixed categories; cash-position and
daily/monthly balance computation; CRUD with many-to-many relations for suppliers, products,
and packaging; Telegram bot commands; and OCR-assisted invoice upload with a mandatory
verification step. There are no roles: every authenticated user has full access to every record.

## Prerequisites

- Node.js ≥ 20 and npm
- A running PostgreSQL instance with the `xpand` database already created and seeded, and a
  role that can read/write it. Set the connection in `DATABASE_URL` (see [Env vars](#environment-variables)).
  > The originally-specified role `xpand/admin` did not authenticate against the local server;
  > it was created only as a database, without that role. The app currently connects as the
  > `postgres` superuser. Create a dedicated `xpand` role when convenient and point
  > `DATABASE_URL` at it.

### Prisma (introspected)

The schema is generated by **introspection**, not hand-written or migrated. Only the
`generator` and `datasource` blocks in [prisma/schema.prisma](prisma/schema.prisma) are
authored by hand; every model below them comes from `prisma db pull` against the live DB.

Regenerate after any change to the database:

```bash
npx prisma db pull      # re-introspect the tables into schema.prisma
npx prisma generate     # regenerate the typed client used by src/db/prisma.ts
```

Do **not** run `prisma migrate` / `db push` — the database is the source of truth and is
managed outside this app.

See [What was introspected vs. assumed](#what-was-introspected-vs-assumed) for the notable
type mappings and caveats.

## Authentication

[src/middleware/auth.ts](src/middleware/auth.ts) accepts two credentials, in this order.

### 1. Mini App `initData` — the real one

```
Authorization: tma <initData>
```

When Telegram opens a Mini App it hands the page an `initData` query string describing who
opened it, signed with a key derived from the bot token. Only Telegram and we know that token,
so a valid signature **proves** the caller is that Telegram user.

[src/utils/telegramAuth.ts](src/utils/telegramAuth.ts) implements Telegram's algorithm:

1. Every `key=value` pair except `hash`, sorted by key, joined with `\n` — the _data check string_.
2. `secret_key = HMAC_SHA256(key: "WebAppData", message: <bot token>)`
3. `expected = HMAC_SHA256(key: secret_key, message: <data check string>)`
4. Constant-time compare against the `hash` field.

Note step 2's unusual order — the literal `"WebAppData"` is the HMAC _key_ and the token is the
_message_. Swapping them yields a validator that rejects everything.

Signatures older than **24 hours** are rejected (`auth_date`), bounding replay of a leaked
string. On this path the user row is **created on first contact** from the verified profile, so
no separate `/login` call is needed.

### 2. `x-telegram-id` header — development only

The original stub, kept so the app works in a plain browser tab where no initData exists. It
trusts an unsigned header, so it is **refused outright when `NODE_ENV=production`**, whatever
else is configured. It never auto-creates a user — an unverified header must not be able to mint
rows — so `POST /api/users/login` has to run first.

### Authorization

There isn't any. Authentication is the only gate: anyone Xpand recognises as a Telegram user
may read and write every record -- all transactions, reports and entities, whoever logged them.
The books belong to the company, not to each employee, and access is controlled by who is given
the bot rather than by what the app grants them once they are in.

No endpoint returns **403**, there is no `requireRole`, and `transactions.user_id` records
_who logged the entry_ -- authorship for the audit trail, never a permission.

The `users.role` column still exists and is always `ADMIN`, its only remaining enum value.
Nothing reads or writes it; it is kept so roles could return without a data migration.

### Production guard

With `NODE_ENV=production` the server **refuses to boot without `TELEGRAM_BOT_TOKEN`** — that
token is the only thing that can verify a signature, so booting without it would leave the app
either unusable or wide open.

## Telegram bot

Commands are shortcuts; the Mini App stays the interface for complex work.

| Command                               | Behaviour                                            |
| ------------------------------------- | ---------------------------------------------------- |
| `/start`                              | Greets, creates the user, shows the app buttons.     |
| `/help`                               | Full command reference.                              |
| `/balance`                            | Cash position, opening balance, all-time in/out/net. |
| `/today`                              | Today's income, expenses, net, entry count.          |
| `/transactions`                       | Last 10 entries + a button into the app.             |
| `/income [amount] [category] [note]`  | Logs income; bare form opens the app.                |
| `/expense [amount] [category] [note]` | Logs an expense; bare form opens the app.            |

```
/expense 250 transport taxi to airport    → logged, with an Undo button
/expense 250,50 transport                 → comma decimals work
/expense 250                              → asks which category
/expense                                  → opens the Mini App form
```

Quick entry defaults to today and cash. Handlers call the service layer directly — same
ownership rules, same category↔type validation as the HTTP API. See
[src/modules/bot/README.md](src/modules/bot/README.md) for the design, the polling-vs-webhook
trade-off, and the timezone caveat.

### Setting it up with @BotFather

1. `/newbot` → choose a name and username → copy the token.
2. Put it in `.env` as `TELEGRAM_BOT_TOKEN`.
3. `npm run dev`. The bot registers its own command menu on startup.
4. To attach the Mini App: `/newapp` in @BotFather, pick the bot, give it the **HTTPS** URL of
   the frontend, then set the same URL as `MINI_APP_URL` in `.env`. Without it the bot still
   answers, just without "Open app" buttons.

### Testing the bot locally

Polling needs no public URL, so the bot works on a laptop as soon as the token is set. The Mini
App _buttons_ do need HTTPS — Telegram rejects `http://localhost`:

```bash
# terminal 1 — frontend
cd ../xpandFront && npm run dev

# terminal 2 — a public HTTPS URL for it
npx cloudflared tunnel --url http://localhost:5173

# then set MINI_APP_URL to the printed https URL, add it to CORS_ORIGINS, and restart:
cd ../xpand && npm run dev
```

Only **one process may poll a token at a time** — a second returns 409 and the two steal each
other's updates. Stop one before starting another.

## API

All bodies and responses are JSON. Success payloads are wrapped as `{ "data": ... }`; errors
as `{ "error": { "message, statusCode, details? } }`. Every route except
`POST /api/users/login` and `GET /health` needs authentication — `Authorization: tma <initData>`,
or `x-telegram-id` in development (see [Authentication](#authentication)).

### Users

| Method & path           | Access | Notes                                          |
| ----------------------- | ------ | ---------------------------------------------- |
| `POST /api/users/login` | public | Upsert on Telegram login. Profile fields only. |
| `GET  /api/users/me`    | auth   | The current user.                              |
| `GET  /api/users`       | auth   | List all users.                                |
| `GET  /api/users/:id`   | auth   | One user by Telegram id.                       |

### Categories

| Method & path                | Access | Notes                                                         |
| ---------------------------- | ------ | ------------------------------------------------------------- |
| `GET    /api/categories`     | auth   | List. `?type=INCOME\|EXPENSE\|BOTH` filter.                   |
| `GET    /api/categories/:id` | auth   | One category.                                                 |
| `POST   /api/categories`     | auth   | Create. Unique name (409 on dupe).                            |
| `PATCH  /api/categories/:id` | auth   | Update (≥1 field). 409 on name clash.                         |
| `DELETE /api/categories/:id` | auth   | **409 if the category is used by any transaction**, else 204. |

### Transactions

| Method & path                  | Access | Notes                                                  |
| ------------------------------ | ------ | ------------------------------------------------------ |
| `GET    /api/transactions`     | auth   | Every user's rows, narrowed by the optional filters.   |
| `GET    /api/transactions/:id` | auth   | Any transaction. **404** only when it does not exist.  |
| `POST   /api/transactions`     | auth   | Attributed to the caller. Category/type rule enforced. |
| `PATCH  /api/transactions/:id` | auth   | Any transaction; re-checks compatibility on change.    |
| `DELETE /api/transactions/:id` | auth   | Any transaction.                                       |

**List filters:** `from`, `to` (inclusive `transaction_date` range, `from ≤ to`),
`categoryId`, `type`, and `userId` to narrow to one person's entries.

**Create/update body** (camelCase): `categoryId`, `type` (`INCOME`/`EXPENSE`), `amount`
(> 0, ≤ 2 decimals), `transactionDate` (`YYYY-MM-DD`), and optional `currency` (3-letter,
default `TND`), `description`, `paymentMethod` (`CASH`/`BANK_TRANSFER`/`CHECK`/`CARD`/`OTHER`,
default `CASH`), `supplierId`, `productId`, `packagingId`.

**Category ↔ type rule:** an `INCOME`/`EXPENSE` category accepts only matching transactions;
a `BOTH` category accepts either. Violations are **400**.

### Reports (financial calculations)

Cash position follows the core principle:

```
Cash Position = Opening Balance + Total Income − Total Expenses
```

| Method & path                  | Access | Notes                                                |
| ------------------------------ | ------ | ---------------------------------------------------- |
| `GET /api/reports/summary`     | auth   | Cash position + today / month income, expenses, net. |
| `GET /api/reports/by-category` | auth   | Income and expenses grouped by category.             |

Both cover **everyone** by default -- the company-wide position is the number Xpand exists to
show -- and `?userId=` narrows either one to a single person.

**`/summary`** returns `openingBalance`, `totalIncome`, `totalExpenses`, `cashPosition`,
`netCashMovement` (all-time), plus `today` and `month` objects (`income` / `expenses` /
`net`). Amounts are strings with 2 decimals.

- `?on=YYYY-MM-DD` — reference date defining "today" and "this month" (defaults to the
  server's current date). Handy for deterministic checks.
- `?openingBalance=NUMBER` — override the configured opening balance for this call.
- All-time totals and the cash position are computed **as of the reference day**, so
  future-dated rows are excluded from "money on hand now".

**`/by-category`** returns `{ income: [...], expenses: [...] }`, each entry
`{ categoryId, categoryName, type, total, count }`, sorted by `total` desc. Filters:
`?from=`, `?to=` (inclusive date range, `from ≤ to`), `?type=INCOME|EXPENSE`.

```bash
curl 'localhost:3000/api/reports/summary?on=2026-08-29&openingBalance=1000' -H 'x-telegram-id: 111'
curl 'localhost:3000/api/reports/by-category?from=2026-08-01&to=2026-08-31' -H 'x-telegram-id: 111'
```

### Suppliers, Products & Packaging

Full CRUD + `?search=` for each, open to any authenticated user -- reads, writes and
relationship link/unlink alike. Deleting an entity that a transaction references returns
**409**; its relationship links cascade automatically.

Each of these has its own README with copy-paste Postman/curl examples:

- [suppliers](src/modules/suppliers/README.md) · [products](src/modules/products/README.md) ·
  [packaging](src/modules/packaging/README.md)

| Method & path                                      | Access | Description                         |
| -------------------------------------------------- | ------ | ----------------------------------- |
| `GET/POST /api/suppliers`, `GET/PATCH/DELETE /:id` | auth   | Supplier CRUD (`?search=` on list). |
| `GET/POST /api/products`, `GET/PATCH/DELETE /:id`  | auth   | Product CRUD (unique `sku`).        |
| `GET/POST /api/packaging`, `GET/PATCH/DELETE /:id` | auth   | Packaging CRUD.                     |

**Relationships** (the three many-to-many links from the DB schema). The write side lives on
one owning module; both sides expose a read view:

| Relationship         | Extra field | Manage (write)                                         | Read views                                                             |
| -------------------- | ----------- | ------------------------------------------------------ | ---------------------------------------------------------------------- |
| supplier ↔ product   | `unitPrice` | `PUT/DELETE /api/suppliers/:id/products/:productId`    | `GET /api/suppliers/:id/products`, `GET /api/products/:id/suppliers`   |
| supplier ↔ packaging | `unitPrice` | `PUT/DELETE /api/suppliers/:id/packaging/:packagingId` | `GET /api/suppliers/:id/packaging`, `GET /api/packaging/:id/suppliers` |
| product ↔ packaging  | `quantity`  | `PUT/DELETE /api/products/:id/packaging/:packagingId`  | `GET /api/products/:id/packaging`, `GET /api/packaging/:id/products`   |

`PUT` is an idempotent upsert — call it again to re-price / change quantity. Entity detail
(`GET /:id`) embeds the linked entities inline.

```bash
curl -X POST localhost:3000/api/suppliers -H 'x-telegram-id: 111' \
  -H 'Content-Type: application/json' -d '{"name":"Acme Foods","email":"ali@acme.tn"}'
curl -X PUT localhost:3000/api/suppliers/1/products/1 -H 'x-telegram-id: 111' \
  -H 'Content-Type: application/json' -d '{"unitPrice":10.50}'
curl -X PUT localhost:3000/api/products/1/packaging/1 -H 'x-telegram-id: 111' \
  -H 'Content-Type: application/json' -d '{"quantity":6}'
```

### Invoices (upload + OCR)

Photograph an invoice; the supplier, date, total, currency and invoice number are read off it; the
user checks them; **then** a transaction is created. Full detail, including the extraction
heuristics and their locale assumptions, in [src/modules/invoices/README.md](src/modules/invoices/README.md).

| Method & path                        | Access | Notes                                                              |
| ------------------------------------ | ------ | ------------------------------------------------------------------ |
| `POST   /api/invoices`               | auth   | `multipart/form-data`, field `file`. 201, status `PENDING`.        |
| `GET    /api/invoices`               | auth   | `?status=` / `?transactionId=`. `meta.awaitingReview` for badging. |
| `GET    /api/invoices/:id`           | auth   | Invoice + `draft`. Poll while `PENDING`/`PROCESSING`.              |
| `GET    /api/invoices/:id/file`      | auth   | The stored image. Never served statically.                         |
| `GET    /api/invoices/:id/raw-text`  | auth   | What the OCR engine read, verbatim.                                |
| `POST   /api/invoices/:id/retry-ocr` | auth   | Read the page again.                                               |
| `POST   /api/invoices/:id/confirm`   | auth   | **Creates the transaction** from the user's verified values.       |
| `POST   /api/invoices/:id/link`      | auth   | Attach to an existing transaction. Creates nothing.                |
| `DELETE /api/invoices/:id`           | auth   | Discards an unconfirmed invoice. 409 once confirmed.               |

**The rule that matters:** an unverified draft is never a transaction. OCR output lives in
`invoices.ocr_extracted_data`; `transactions` gains a row only on confirm, from values the user
submitted. So the cash position cannot include a number nobody has checked — no report needs to
know drafts exist.

`status`: `PENDING` → `PROCESSING` → `READY` (or `FAILED`) → `CONFIRMED`. `FAILED` is still
reviewable: the user fills the draft by hand. Uploads are **images only** (`image/jpeg`,
`image/png`, `image/webp`) — a PDF is refused up front, since Tesseract reads pixels.

```bash
# Upload, then poll for the extraction
curl -X POST localhost:3000/api/invoices -H 'x-telegram-id: 111' -F 'file=@invoice.jpg'
curl localhost:3000/api/invoices/1 -H 'x-telegram-id: 111'

# Confirm — these values, not the OCR's, become the transaction
curl -X POST localhost:3000/api/invoices/1/confirm   -H 'x-telegram-id: 111' -H 'Content-Type: application/json'   -d '{"categoryId":2,"amount":"458.15","transactionDate":"2026-09-18","supplierId":6}'
```

## What was introspected vs. assumed

**Introspected** (read directly from the DB via `prisma db pull` — the source of truth):

- **10 models / 4 enums**, all relations and FKs. Enums: `role{ADMIN}` (vestigial),
  `category_type{INCOME,EXPENSE,BOTH}`, `transaction_type{INCOME,EXPENSE}`,
  `payment_method{CASH,BANK_TRANSFER,CHECK,CARD,OTHER}`.
- **`users.id` is `BIGINT`** → Prisma `BigInt` (Telegram ids can exceed 2^53). Handled: ids
  are serialized to **strings** in JSON (see [utils/serialization.ts](src/utils/serialization.ts))
  to avoid `JSON.stringify` throwing and to preserve precision.
- **`transactions.amount` is `NUMERIC(12,2)`** → Prisma `Decimal`; returned as a string.
- **Field names are snake_case** (`first_name`, `transaction_date`, `payment_method`, …). The
  API translates to/from camelCase at the controller boundary.
- FK `ON DELETE NO ACTION` from transactions → categories/users/suppliers/products/packaging,
  so deleting an in-use row is a DB error; the delete paths pre-check and return a clean 409.
- **Junction FKs are `ON DELETE CASCADE`** (supplier_products, supplier_packaging,
  product_packaging), so deleting a supplier/product/packaging drops its links automatically.
  Composite PKs are used as Prisma `where` keys (e.g. `supplier_id_product_id`).

**Flagged, not silently fixed:**

- ⚠️ **Dropped CHECK constraints.** Introspection warned that Prisma doesn't model
  `transactions.amount > 0` or `product_packaging.quantity > 0`. The DB still enforces them,
  but Prisma won't — so `amount > 0` is **also** validated in Zod (the real guard at the API
  layer). Left the DB constraints as-is.
- ⚠️ **Seeded category name `'charges fixes'` has a space** (not `charges_fixes`). Left exactly
  as seeded; the mirror in [constants.ts](src/config/constants.ts) matches the DB.
- ⚠️ **`transactions.updated_at`** has only `DEFAULT now()` (no `@updatedAt`), so it doesn't
  auto-bump. The update service sets it explicitly.
- ⚠️ **`transaction_date` is `DATE`** (no time) → accepted as `YYYY-MM-DD`, returned as
  `YYYY-MM-DD`.

**One deliberate DB change (authorized):** the `transactions.currency` column default was
`ALTER`ed from `'DZD'` to `'TND'` (and any existing `DZD` rows updated) as part of the currency
switch. `schema.prisma` was re-pulled so `@default("TND")` reflects it. The app also sets
`currency = 'TND'` explicitly on new transactions, so it's correct even against an un-altered DB.

**Assumed** (product decisions, not derived from the DB):

- Dev auth via `x-telegram-id` header; login upsert writes profile fields only.
- **No authorization tier.** Every authenticated user can read and write everything — the
  company's books are shared. `transactions.user_id` is authorship, not ownership.
- **Suppliers / products / packaging** — the same: fully open to any authenticated user.
  Deleting an entity referenced by a transaction → 409. Relationship `PUT` is an idempotent
  upsert; the write side of each link lives on one owning module — a data-model rule, not a
  permission.
- **Reports — opening balance** has no column in the DB, so it comes from `OPENING_BALANCE`
  (env, default 0), overridable per request via `?openingBalance=`. Store it in the DB later
  if it needs to be per-account or audited.
- **Reports — single currency.** Amounts are summed as-is assuming one currency (`TND`); there
  is **no FX conversion**. Mixed-currency data would need grouping/conversion first.
- **Reports — "current" excludes the future.** Cash position and all-time totals are computed
  as of the reference day, so future-dated transactions don't inflate money on hand.
- **Reports — dates are UTC.** Day/month boundaries are computed in UTC to match the `DATE`
  column, which Prisma reads at UTC midnight.

## Deployment (Vercel + Supabase, free tier)

The backend runs as a single Vercel serverless function: `api/index.js` builds the same
`createApp()` the local server does, and `vercel.json` rewrites every path to it. Routing,
middleware order and error handling are therefore identical on both hosts — only the transport
differs.

### What serverless changes, and why

Four things do not survive a read-only, frozen-between-requests runtime. Each is handled rather
than worked around:

| Local behaviour                               | On Vercel                                                                                                                                                                                                                                                                             | Where                             |
| --------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------- |
| `app.listen()` + graceful shutdown on SIGTERM | The platform owns the socket; instances are frozen, never signalled. `api/index.js` exports a handler and skips the lifecycle entirely.                                                                                                                                               | `api/index.js`                    |
| Bot **polls** Telegram                        | Polling needs a process that outlives a request. Mode defaults to `webhook`, and the route initialises the bot on demand — nothing runs `startBot()` there. Registration is a one-off (`npm run bot:register`), because a cold start per traffic burst would re-register on each one. | `src/modules/bot/index.ts`        |
| Invoice files written to `UPLOAD_DIR`         | The filesystem is read-only apart from `/tmp`, and `/tmp` is gone before the user opens the review screen. Files go to a **private** Supabase Storage bucket instead.                                                                                                                 | `src/modules/invoices/storage.ts` |
| OCR runs **after** the response               | The instance is frozen the moment a response is written, so a background pipeline is killed partway and the invoice never leaves `PENDING`. `OCR_SYNC` awaits it, so the response already carries the draft.                                                                          | `src/modules/invoices/service.ts` |

The server refuses to boot on a serverless host without Supabase credentials, rather than
accepting uploads it cannot keep.

### Database

Use the Supabase **transaction pooler** string (port `6543`) as `DATABASE_URL`, with
`?pgbouncer=true&connection_limit=1`. Every serverless instance opens its own pool, so direct
connections on port `5432` exhaust a free project within minutes of real traffic. The two query
parameters are not optional: `pgbouncer=true` stops Prisma using prepared statements, which a
transaction-mode pooler cannot hold across statements.

`prisma/schema.prisma` stays **introspected** — do not run `migrate` or `db push`. Move the
schema with `pg_dump` instead, which is the only way the two `CHECK` constraints survive
(`transactions_amount_check`, `product_packaging_quantity_check`); Prisma cannot express them, so
anything generated from the datamodel would silently drop them and let a negative amount in.

```bash
# 1. Schema and data out of the local database.
pg_dump -U postgres -h localhost -d xpand --schema-only --schema=public \
  --no-owner --no-privileges --no-publications --no-subscriptions -f 01-schema.sql
pg_dump -U postgres -h localhost -d xpand --data-only --schema=public \
  --no-owner --no-privileges -f 02-data.sql

# 2. Three statements must be stripped before a managed host will accept it:
#      CREATE SCHEMA public       - already exists, aborts the script
#      COMMENT ON SCHEMA public   - not ours to comment on
#      SET transaction_timeout    - PostgreSQL 17 only; a PG15 instance rejects it
#    Do NOT pass --disable-triggers to the data dump: it emits ALTER TABLE ... DISABLE TRIGGER
#    ALL, which needs true superuser rights no managed host grants. The COPY blocks come out in
#    parent-before-child order, so the foreign keys hold without it.

# 3. In, over the DIRECT connection (port 5432) — poolers and DDL do not mix.
psql "$DIRECT_URL" -v ON_ERROR_STOP=1 -f 01-schema.sql -f 02-data.sql
```

Never pipe `psql` into `head`: the pipe closing early sends SIGPIPE, `psql` dies partway, and
because the trailing `setval` calls are the last thing in a dump the sequences are left unset.
Everything looks fine until the first insert collides with an existing id.

Verify the sequences landed — this is the failure that hides:

```bash
psql "$DIRECT_URL" -At -c \
  "SELECT sequencename, last_value FROM pg_sequences WHERE schemaname='public' ORDER BY 1;"
```

### Invoice files

Create the bucket as **private** (Storage → New bucket, "Public" unchecked). Files are served
only through `GET /api/invoices/:id/file` so `requireAuth` sits in front of them; a public bucket
would put every receipt the company has behind a guessable URL. Then move the existing files:

```bash
npm run files:migrate -- --dry-run   # what would be uploaded
npm run files:migrate                # upload it
```

It is driven by the `invoices` rows rather than a directory listing, so it uploads exactly what
the app can reach and reports rows whose bytes are already gone.

### Order of operations

The two deployments each need the other's URL, so one pass cannot settle both:

1. Deploy the frontend → note its URL.
2. Deploy the backend with `CORS_ORIGINS` and `MINI_APP_URL` set to that URL.
3. Rebuild the frontend with `VITE_API_BASE_URL` set to the backend URL. Vite inlines env vars at
   **build** time, so setting the variable is not enough — it needs a fresh deployment.
4. `npm run bot:register` with `BOT_WEBHOOK_URL` set to the backend URL.
5. @BotFather → `/myapps` → Edit Web App URL → the frontend URL.

### Caveats worth knowing

- **A free Supabase project pauses after 7 days with no activity.** The first request after that
  fails until it is restored from the dashboard. Real daily use never hits this.
- **Vercel's Hobby plan is for non-commercial use.** This is an internal company tool, which is
  not obviously within that. Worth reading the current terms before it matters.
- **Cold-start OCR re-downloads language data.** `TESSDATA_DIR` lives under `/tmp`, which does not
  survive, so each cold start fetches ~6 MB of `*.traineddata` again. Committing the files and
  copying them into `/tmp` at startup would remove the round trip if it proves slow.

### `includeFiles` is load-bearing for OCR

Vercel bundles a function by statically tracing its imports, and tesseract.js defeats that twice:

- `src/worker/node/defaultOptions.js` builds its worker path with `path.join(__dirname, …)` and
  hands it to `new Worker()`. A computed path is invisible to the tracer, so neither the worker
  script **nor anything it requires** is traced.
- the Emscripten cores `readFileSync` their `.wasm` sibling by name at runtime.

Both are listed explicitly in `vercel.json` instead. Without them the deploy succeeds, the API
works, and OCR fails at the first upload with a module-not-found error from inside a worker
thread — which is a long way from the cause.

Only the `*lstm*` cores are included, not all eight variants: `ocr.ts` calls `createWorker` with
`oem = 1` (`LSTM_ONLY`), and `worker-script/node/getCore.js` can only reach an `-lstm` build on
that branch. That is 20 MB rather than 44 MB, which matters because Prisma's query engine already
spends a large share of the 250 MB unzipped function budget. If the OEM ever changes, widen the
glob to `node_modules/tesseract.js-core/**`.

## What's next

1. **PDF invoices.** Uploads accept images only, because Tesseract is an image OCR engine; a
   PDF is rejected up front with a message telling the user to photograph it. Supporting PDF
   means reading the embedded text layer (pure JS, but absent on scanned PDFs) or rasterising
   first (native dependencies). See the invoices README.
2. **Wider test coverage.** `npm test` (Node's built-in runner, via `scripts/test.mjs`) covers
   the OCR field extraction against real Tesseract output. `src/utils/telegramAuth.ts` and
   `src/modules/bot/parse.ts` are pure and the obvious next targets.
3. **Per-user timezone.** Report boundaries and bot entries use UTC; the Mini App pins the
   client's local day. Near midnight in UTC+1 the two can disagree by a day. A `timezone`
   column on `users` would settle it for both surfaces.
